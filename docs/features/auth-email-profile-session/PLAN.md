## Solución propuesta

### Límites de responsabilidades

- **Kotlin Multiplatform (`commonMain`):** validaciones compartidas aprobadas para nombre, email y contraseña; modelos/resultados de sesión y errores neutrales; coordinación de casos de uso para registro, acceso, reenvío y comprobación de verificación, recuperación de perfil y cierre; lectura/escritura local del perfil; control de la política de acceso limitada por estado; cálculo de qué identidad puede abrir una base local. No debe importar `FirebaseAuth`, `FirebaseFirestore`, Android ni Swift.
- **Android (`androidApp`):** implementación del puente público desde Firebase Android Auth/Firestore, configuración Firebase Android, integración con el ciclo de vida Compose, manejo de enlaces de acción del correo mediante Android App Links, presentación nativa y consumo de la fachada compartida.
- **iOS (`iosApp`):** implementación equivalente con Firebase Apple SDK por Swift Package Manager, inicialización SwiftUI/AppDelegate, Universal Links, presentación SwiftUI y consumo de la fachada KMP. Antes de diseñar el puente definitivo, comprobar en una llamada real Swift la interoperabilidad de suspend functions, resultados sellados y errores Kotlin exportados; no dar por demostrado que un contrato común se consume cómodamente desde Swift.
- **Backend Firebase:** Firebase Authentication para identidad y correo verificado; Cloud Firestore para el perfil remoto con una ruta determinista por UID. Las reglas de este incremento permiten a una persona leer/crear/actualizar solo su perfil. No se habilitan hogares/inventario; las rutas no contempladas quedan denegadas. Las reglas futuras de hogares deberán exigir sesión autenticada, pertenencia y las condiciones de verificación aprobadas.

### Recorrido principal

1. En el arranque, cada app muestra estado de restauración y consulta al proveedor nativo. El UID autenticado selecciona exclusivamente la partición local de esa cuenta. Sin UID, se cierra cualquier contexto local activo y se presenta el acceso.
2. Para la sesión autenticada, se carga el perfil de su Room y se obtiene el estado de verificación conocido. Con conexión se refresca Firebase Auth y se consulta Firestore por `users/{uid}`. Si no existe perfil local pero sí remoto, se guarda el snapshot localmente sin generar outbox, sujeto a la comprobación transaccional del punto 4. Solo una respuesta remota positiva de “no existe” permite solicitar nombre/completar el perfil; error remoto mantiene la sesión y da reintento. Si existe perfil local válido y el remoto falla, se conserva el local y se comunica el error recuperable.
3. Registro/acceso validan localmente en `commonMain`, llaman al puente nativo de Firebase y traducen errores SDK a categorías neutrales. Al registrar, la identidad autenticada conserva su UID; se crea el perfil remoto de forma idempotente para ese UID y se persiste localmente sin crear otro usuario. Si falla una parte, la sesión permanece y el reintento usa el mismo UID, sin reemplazar un perfil local con una respuesta remota antigua.
4. El estado verificado solo se actualiza tras confirmación de Firebase. Si existe una confirmación previa guardada para el mismo UID, puede restaurarse offline con acceso limitado según la SPEC; no habilita hogares/inventario por sí sola. Al volver conexión se refresca Auth y se vuelve a evaluar el estado.
5. Antes de habilitar acciones de hogar/inventario, la UI dirige al estado limitado y los casos de uso/repositorios de datos protegidos consultan una puerta compartida de sesión/verificación. En particular, proteger las operaciones de `HouseholdRepository` y `ItemRepository`, no solo la navegación ni `CreateHouseholdUseCase`. La creación de hogar existente debe rechazar sesión no verificada; las lecturas locales de hogar/objeto también deben quedar denegadas. Los DAOs son internos y se acceden mediante esas operaciones protegidas. Las reglas remotas del perfil restringen por UID; las reglas para recursos de hogar/inventario permanecen cerradas hasta su incremento.
6. Al cerrar sesión, primero se comunica si existen operaciones pendientes y se ofrecen las opciones aprobadas: cancelar o cerrar conservándolas. En este incremento no se sincroniza. Al confirmar, se bloquea inmediatamente la presentación de datos, se termina la sesión local Firebase, se cierra el acceso al contexto Room actual y se limpia estado de navegación/formulario sensible. La base, sus archivos y outbox no se borran. La siguiente identidad recibe otra partición. Offline se sigue el mismo cierre local y se informa que hace falta conexión para volver a autenticarse.

### Partición local por UID

**Recomendación técnica:** cambiar los builders de base compartida única a una base Room por identidad autenticada, almacenada bajo un nombre determinista no reversible derivado del UID. El contenedor de aplicación entrega un `MisCosasDatabase` solo después de conocer el UID y lo cierra/invalida al salir de sesión o cambiar de identidad. Todas las pantallas, repositorios, caches y consultas de outbox deben depender de esa instancia activa; no mantener repositorios singleton que capturen una base anterior. Los datos globales previos al login no se exponen a una cuenta.

Esto evita alterar ahora todas las tablas/DAO de hogares, objetos, documentos, fotos y outbox para añadir `ownerUid` y obliga a que un nuevo UID no pueda consultar operaciones ajenas. Como alternativa, una sola base con columna owner UID y filtros obligatorios en cada tabla/consulta evita varios archivos, pero exige una migración y auditoría amplia de todas las entidades, DAOs y transacciones; un filtro omitido puede cruzar cuentas. Se recomienda partición física para este incremento, coherente con S30 y la arquitectura actual.

**Inventario seguro de `miscosas.db`:** antes de cambiar los builders, cerrar normalmente la aplicación e identificar la ruta local mediante los mecanismos existentes (`Context.getDatabasePath` en Android y Application Support en iOS). No abrir el archivo con Room ni desde el contexto de una cuenta autenticada: Room puede inicializar o migrar el esquema. Para comprobar si contiene datos reales, una herramienta de diagnóstico local de solo lectura puede conectarse a SQLite con `query_only` y consultar exclusivamente `sqlite_master`, `PRAGMA user_version`, `PRAGMA integrity_check` y `COUNT(*)` para las once tablas Room de dominio (`users`, `households`, `household_members`, `items`, `documents`, `warranties`, `return_periods`, `maintenance_tasks`, `maintenance_records`, `item_history_events`, `sync_outbox`). No leer, copiar a logs ni mostrar valores de filas. Un archivo inexistente o tablas de dominio vacías indica que no se encontraron registros; una o más filas significa contenido legacy que debe permanecer aislado. El recuento no demuestra a qué UID pertenece.

La antigua `miscosas.db` y cualquier archivo asociado se preservan en su lugar sin abrirlos desde una identidad nueva, borrar, renombrar ni reasignar. Si fuese necesaria una copia diagnóstica, se hará únicamente con la app y la base cerradas y se conservarán como una unidad `miscosas.db`, `miscosas.db-wal`, `miscosas.db-shm` y el directorio privado de archivos asociados; no se limpiarán ni separarán sidecars. Hoy `DocumentEntity` guarda metadatos y no se encontró un almacenamiento local implementado para archivos, pero la inspección de solo lectura del área privada deberá comprobarlo antes de cualquier migración futura. No se implementa migración legacy en este PLAN.

La detección de pendientes de cierre consultará el outbox de la partición del UID autenticado (hoy `findAllPending()`), no una instancia global. Para fuentes ya existentes, mostrar el aviso antes de cerrar; confirmar cierre solo conserva la base. No se crea un motor de envío, reintento ni resolución de conflictos. No hay hoy almacenamiento de conflictos ni repositorio de notificaciones en el código inspeccionado; su ausencia no permite afirmar que CA-30 esté implementado y CA-30 sigue diferido.

## Datos y contratos

- **Modelos y contratos de entrada y salida:** reutilizar `User`, `UserId` e `Instant`. Ampliar el estado de sesión y los resultados públicos necesarios para que Compose y SwiftUI reciban estados/errores serializables o interoperables; revisar la API exportada real a Swift antes de fijarla. Añadir un modelo neutral de error (validación local, credenciales/cuenta, conexión/temporal, límite, perfil remoto, error inesperado y cancelación); el mapeo SDK queda en adaptadores. No exportar `RegistrationPartiallyCompletedException` interna a Swift.
- **Identificadores, relaciones y restricciones:** el documento Firestore será `users/{firebaseUid}` y su campo ID debe concordar con el UID autenticado; no aceptar UID de formulario. Perfil local y snapshot de verificación se guardan dentro de la partición con esa UID. Prohibir que la partición activa cambie si la app aún expone una sesión anterior.
- **Origen de los datos mostrados y transformaciones:** Room para UI tras login/restauración; Firebase Auth es autoridad para identidad y verificación cuando hay conexión; Firestore es autoridad remota del perfil. El SDK nativo no entrega modelos Firebase a UI ni dominio. Una ausencia local no implica ausencia remota.
- **Persistencia, consultas y actualizaciones:** añadir operación de aplicación remota en Room que escribe `UserEntity` sin outbox; mantener `save()` para cambio iniciado localmente y outbox atómico. Antes de aplicar un snapshot remoto, comprobar dentro de la misma `withWriteTransaction` si existe una mutación local pendiente para el mismo perfil (el outbox actual identifica el objetivo por `scopeId`, `recordTypeCode` y `recordId`). Si existe, no escribir el snapshot, no alterar ni borrar el outbox, y conservar el perfil local como pendiente; el snapshot remoto permanece en el servidor. Si no existe mutación pendiente, aplicar el snapshot remoto sin crear outbox. Leer perfil remoto por UID; crear solo tras confirmación de ausencia. Al autenticar cuenta nueva, abrir su DB, nunca reutilizar DAO/caches de la anterior.
- **Convivencia entre datos locales y remotos:** restauración con red: recuperar Auth UID, cargar perfil local, refrescar verificación y consultar perfil remoto cuando corresponda según CA-12..15. Un error remoto no elimina el perfil local. Si hay mutación pendiente, posponer la aplicación del snapshot; no decidir ganador por fecha ni mostrarlo como sincronizado. Este tratamiento conserva el valor local y la operación pendiente, pero no resuelve la posible diferencia con el servidor ni implementa UI/motor de conflicto; esa resolución queda para la sincronización general. Sin red, solo usar estado de verificación positiva previamente guardado para la misma UID; sin evidencia, mantener acceso limitado. Una escritura local que no llegó al servidor conserva su outbox hasta el incremento que pueda procesarla.
- **Compatibilidad y migraciones de datos existentes:** `miscosas.db` actual no registra propietario UID. Antes de cambiar builders se inventaría solo el número de filas de sus tablas de dominio mediante SQLite de solo lectura, sin pasar por Room ni leer valores; cualquier fila supone conservar la base completa y mantenerla fuera de las particiones autenticadas. Preservar también WAL/SHM y el área privada asociada; no asignar, mover o borrar. No se necesita conocer ahora el contenido real ni implementar migración para aprobar este PLAN. Las migraciones Room futuras se aplicarán dentro de cada partición nueva.

## Estado, operaciones y errores

- **Gestión del estado de interfaz y navegación:** estado raíz observado desde composición nativa: restaurando, sin sesión, sesión limitada por verificación, perfil pendiente, listo, o error recuperable asociado a sesión. Evitar un frame de login antes de completar restauración (CA-16). Un acceso autenticado no equivale a correo verificado.
- **Conservación y restauración del estado:** nombre/correo temporales durante flujo vivo; contraseña únicamente en formulario activo y nunca persistida. UID y perfil persistidos; verificación positiva offline asociada a UID. Cerrar sesión limpia campos secretos, navegación y suscripciones del usuario, preservando la partición y outbox. Las contraseñas no se registran en logs ni almacenamiento.
- **Ejecución, concurrencia y cancelación de operaciones:** proteger envío repetido mientras una operación idéntica está en curso; al cancelar la vista no convertir cancelación de coroutine en fallo genérico. Orden de cierre: hacer inaccesibles UI/estado, cancelar collectors/operaciones de esa identidad, desvincular/cerrar contexto de base, luego cierre local Firebase; manejar callbacks tardíos comprobando UID/epoch de sesión para que no repueblen pantalla de otra cuenta. Evitar cerrar DB mientras siga usándose por una operación autorizada.
- **Errores, reintentos y prevención de duplicados:** mapear códigos nativos a mensajes neutrales aprobados; distinguir “perfil ausente confirmado” de error, timeout o sin conexión. Alta parcial conserva Firebase UID; reintento de perfil no invoca create-account. Reenvío confirma solo solicitud aceptada por Firebase. Writes remotos por UID son idempotentes. Fallo al cerrar base/limpiar contexto debe dejar datos ocultos y permitir reintento seguro, sin borrar pendientes.
- **Otras consideraciones mobile aplicables y su solución:** Android procesa intent inicial y enlaces recibidos con app activa y vuelve a consultar/verificar Firebase al foreground; iOS hace lo equivalente en ciclo de vida SwiftUI. Teclado, foco, lector de pantalla, textos largos y tamaños dinámicos se validan nativamente. No almacenar contraseña en SavedState, Keychain, UserDefaults, preferencias ni Room; solo estado de vista mientras el formulario vive. Firebase persiste su propio estado de autenticación según el SDK; confirmar comportamiento en ejecución Android/iOS.

## Orden de implementación

Este orden propone cortes verificables; no genera TASKS ni autoriza iniciar implementación. Cada corte requerirá la autorización de fase y trabajo acordada con Rafael.

1. **Comprobar interoperabilidad mínima Kotlin–Swift.** Crear un corte técnico acotado que consuma desde Swift una operación neutral exportada por KMP. Verificar el mecanismo real de llamada y el resultado/error exportados antes de consolidar los contratos de autenticación. Si se necesita un adaptador Swift delgado, mantendrá la invocación/adaptación de interoperabilidad; las reglas de negocio seguirán en `commonMain`.
2. **Inventariar en solo lectura la base y los archivos legacy.** Con la aplicación cerrada, comprobar si existe `miscosas.db`, su integridad y recuentos de filas sin leer valores privados; localizar y preservar juntos la base, sus sidecars y los archivos privados asociados. No abrirla desde una cuenta, borrar, renombrar, atribuir a un UID ni migrar contenido. Si aparecen datos, mantenerlos aislados y registrar evidencia no sensible.
3. **Aislar contexto local por UID.** Cambiar contenedor/builder por plataforma para que no exista una base autenticada activa antes del UID y que logout cierre/desasocie la instancia. Crear/abrir solo la partición de la identidad autenticada y comprobar dos UID y conservación independiente de sus datos/outbox. La antigua base permanece intacta y sin asignación.
4. **Modelar estados y restauración con falsos.** Después de la prueba de consumo Swift, extender estados/contratos comunes y resolver sesión, perfil local/remoto y errores sin Firebase real. Añadir tests unitarios para ausencia local vs remota, error remoto, estado verificado offline por UID, cancelación y snapshot remoto recibido mientras existe un outbox local del mismo perfil.
5. **Inicializar Firebase de desarrollo y conectar acceso email/password.** Antes de instalar la configuración cliente, comprobar y completar los patrones de `.gitignore` para `google-services.json` y `GoogleService-Info.plist`; después instalarla localmente, sin versionar los archivos reales. Usar Emulator Suite para Auth/Firestore, implementar el puente Auth, validadores comunes y mapper de errores; completar acceso antes del alta. Mostrar resultados en Compose/SwiftUI y comprobar reglas contra Emulator.
6. **Completar alta y perfil recuperable.** Integrar registro con UID actual y persistencia remota determinista. Separar `save local + outbox` de `apply remote`; proteger la aplicación remota con una transacción que compruebe el outbox del mismo perfil. Si existe una mutación pendiente, conservar sin cambios el perfil local y el outbox y no marcarlo sincronizado. Probar reintento sin segunda cuenta.
7. **Restaurar sesión, verificar por enlace y cerrar de forma segura.** Conectar restauración, perfil local/remoto, verificación y puertas de acceso; configurar App/Universal Links y adaptar el diseño iOS código→enlace. Completar formularios y logout Compose/SwiftUI, conservando outbox y aislando UID. La sincronización al cerrar y CA-30 permanecen diferidos.
8. **Recorrido de aceptación y seguridad por plataforma.** Ejecutar matrices CA aplicables, Firebase Auth/Firestore Rules Emulator, integración Room real y pruebas controladas de enlaces/ciclo de vida. Registrar CA-30 como diferido, diferencias visuales resueltas y evidencia separada Android/iOS.

## Riesgos y decisiones pendientes

- **Riesgos y medidas acordadas:**
  - **Una única Room DB actual puede cruzar identidades:** introducir partición por UID antes de permitir cambios de cuenta; testear dos cuentas y scopes del outbox. Preservar sin atribución automática la DB anterior.
  - **La aplicación remota accidental puede generar un outbox duplicado:** separar `save` (mutación local) y `applyRemote` (snapshot remoto) y probar transacción/ausencia de outbox.
  - **Proveedor Firebase no existe en la composición:** integración nativa independiente puede divergir; mapear errores/resultados a un contrato común y ejecutar matriz espejo Android/iOS.
  - **El enlace puede abrir navegador o perder el retorno:** configurar dominios actuales HTTPS, App Links/Universal Links y verificar estado mediante Firebase, no confiar en URL o callback solamente.
  - **Perfil local puede ser válido mientras la consulta remota falla:** mostrar/reusar local sin declarar ausencia ni reemplazarlo; error recuperable y reintento.
  - **Swift interop de la fachada KMP:** probar consumo real desde Swift temprano; si el puente suspend/Result no es práctico, usar adaptador Swift delgado manteniendo dominio neutral, sin duplicar reglas.
  - **Datos legacy sin UID:** mantener fuera de particiones autenticadas y no descartarlos; si hay contenido no atribuible, no completar migración/cambio seguro hasta resolver cómo conservarlo.
  - **Pantallas contienen acciones de proveedor ya aprobadas en V1 global (Google/Apple) y la de Android incluye confirmación de contraseña, pero estos comportamientos están fuera de esta SPEC o no están definidos por ella:** no conectar Google/Apple aquí ni inventar validación para confirmación. Revisar la presentación de estas acciones con Rafael antes de cerrar TASKS de UI para no mostrar acciones engañosas ni alterar el alcance V1.
  - **Figma carece de estados de carga/error/recuperación y muestra código en iOS:** integrar los estados con sistema visual actual; enlace en iOS es discrepancia pendiente de adaptación, no cambio de requisito.
- **Cuestiones operativas previas a tareas:** la estrategia ya aprobada es proyecto Firebase de desarrollo con Emulator Suite; al preparar TASKS se comprobarán disponibilidad/ID del proyecto, dominio HTTPS para enlaces y versiones compatibles. Los archivos reales de configuración cliente se instalarán localmente y no se versionarán; las credenciales privadas de servidor nunca irán en cliente ni Git. El inventario real del legado se hará sin leer valores privados y no cambia la decisión de preservarlo sin atribución ni migración en este incremento. El resultado de interoperabilidad Swift sigue siendo una comprobación técnica del primer corte, no una decisión funcional pendiente. Las acciones Google/Apple y la confirmación de contraseña visibles en Figma no pertenecen a esta SPEC; su presentación debe aclararse antes de cerrar las tareas de UI para no ofrecer acciones no conectadas ni cambiar el alcance global aprobado.
